## 1. フォルダの置き場所 → 非公開の別リポジトリに切り出す（このまま公式サイトに合流させない）

**理由**：公式サイトの公開設定（`.github/workflows/static.yml`）は「リポジトリ全体をそのまま公開する」形になっている。
この作業のプルリクエストの合流先は、そのサイトを公開しているブランチ（`claude/ether-arch-company-site-qfyn98`）。
合流すると、`music-label/` の設定書（アーティストのプロフィール、好きな実在アーティスト名）・戦略資料・データベース設計が
**公式サイトから誰でも見られる状態**になる。最初に決めた「クローズドな環境」と矛盾する。

**やり方**（GitHub で非公開リポジトリを 1 つ作ってから、Mac のターミナルで）

```
# 1. GitHub で New repository → 名前 etherarchi-label → Private → 作成（README などは付けない）
# 2. 今のリポジトリから music-label だけを取り出して、新しいリポジトリに送る
cd ~/Eather-Archi
git fetch origin claude/jolly-edison-bzgnjf
git checkout claude/jolly-edison-bzgnjf
git subtree split --prefix=music-label -b label-only
git push https://github.com/5newold111/etherarchi-label.git label-only:main
# 3. 新しいリポジトリを手元に持ってきて、鍵と作業データを移す
cd ~ && git clone https://github.com/5newold111/etherarchi-label.git
cp ~/Eather-Archi/music-label/.env ~/etherarchi-label/.env
cp -R ~/Eather-Archi/music-label/out ~/etherarchi-label/out 2>/dev/null || true
# 4. 定期実行を入れていたら、新しい場所で登録し直す
cd ~/etherarchi-label && python3 scripts/schedule.py install
```

移したあと、公式サイトのリポジトリのこのプルリクエストは「合流せずに閉じる」。

## 2. SNS のアカウント → まずレーベル単位で 1 組ずつ

**理由**：組ごとに作ると、アカウント作成・本人確認・API の許可・審査が組の数だけ増える（Postdog Records だけで 5 倍、子レーベルを入れると 17 倍）。
YouTube は 1 プロジェクト 1 日 6 本までのアップロード枠もある。最初はレーベルのアカウントで全組を発信し、説明文と動画の中で組の名前を出す。

**伸びた組だけ独立させる**：成長分析で「伸びている（up）」が続いた組は、その組専用のアカウントを作り、鍵の名前の後ろに組の名前を付けて入れる
（例 `YOUTUBE_REFRESH_TOKEN__LIGHT`、`IG_ACCESS_TOKEN__LIGHT`）。投稿の仕組みは、組専用の鍵があればそちらを優先する。

| レーベル | YouTube | Instagram | TikTok |
|---|---|---|---|
| Postdog Records | 1 チャンネル | 1 アカウント | 1 アカウント |
| 子レーベル | 立ち上げるときに、レーベルごとに 1 組ずつ（鍵は `__FOCUS` など） | 同じ | 同じ |

  同じ組の次の曲では、下書きの「Artist already in Spotify?」が「Yes（その ID）」になり、ページが 2 つに分かれない

## 27. 参考データベースを、既存の組のこれからの作曲に組ごとに効かせる（2026-10-22）

オーナーが参考データベース（SSD の「データベース」）を作ったので、全体の傾向だけでなく、**組ごとに「この組に近い曲」を割り出して**使う。

- 取り込み（`reference_db.py`。毎週の制作の前にも自動で動く）のたびに、組ごとの近い参考曲を作る：`out/reference_db/artists/<組>.json`・一覧は `out/reference_db/artists.md`
  - 近さ＝設定書のジャンル・特徴語とデータベースのジャンル・タグ・楽器の言葉の重なり（6 割）・テンポ（倍・半分のノリも同じとみる。2.5 割）・声の性別（1.5 割）。日本語の言葉（アコギ・雨・夜 など）は英語に直して比べる
  - 言葉が 1 つも本当に重ならない曲は、テンポと声が合っても近いとみない
  - データベースに **「使う組」の欄**（または メモ）に組の名前（例：TIDEWOOL）を書いた曲は、その組で最優先にする
  - SSD が無いときも、前回の取り込みから作り直す（`python3 scripts/reference_db.py --artists`）
- 使う場所：
  | どこで | どう効くか |
  |---|---|
  | 参考曲の割り当て（`select_references.py`） | 近い曲ほど選ばれやすい（重み 1〜3 倍）。1 曲 1 枠・ボーカル 6:2:2 の決まりはそのまま |
  | ブリーフ作り（`write_brief.py`） | Claude に「この組に近い曲の傾向」（タグ・テンポ・テーマ・楽器・声・オーナーのメモ）を、全体の傾向より重く渡す。実名は伏せる |
  | Suno のスタイル欄（`suno_design.py`） | 近い曲に 2 曲以上出てくる英語のタグで、設定書にまだ無く、禁止・除外に当たらないものを、いちばん後ろに最大 4 つ足す（いちばん弱く効く位置）。止めるときは `templates/suno_options.json` の `use_reference_db` を false |
- 組の音の決まり（設定書）が先で、データベースはその中での好みの寄せ方。実在の名前は Suno にも Claude にも入れない（今までどおり）

## 28. 外出先でもスマホで、作曲から DistroKid の登録まで進められるようにする（2026-10-22）

- つなぐ道は **Tailscale**（Mac とスマホだけの専用の通り道）。`tailscale serve --bg 8765` で、自分の機器だけから https で開く。ルーターのポート開放はしない
- **スマホのページ** `/phone`（`scripts/phone.py`）：曲ごとに、Suno の欄の順の「写す」ボタン（設計図は suno_design.py と同じ）→ スマホから曲を Mac に送る（`/api/upload`。Mac の「楽曲情報」に曲名で置き、取り込みを始める）→ DistroKid の下書きの「写す」と、音源・ジャケットをスマホに保存 →「登録した」の記録
- 自動入力（Mac の専用の Chrome）を使いたいときは、画面共有で Mac を操作する道も残す（ページの下のボタン）
- `.env` の `WEBAPP_AWAKE=1`：ダッシュボードが動いている間、Mac が勝手に眠らない（caffeinate）。`WEBAPP_LAN=1`：家の Wi-Fi から合鍵つきで開ける（`--lan` と同じ）
- 手順は `docs/18_phone.md`。Create と最後の登録ボタンは今までどおり Gon さんが押す

## 29. 追加でデビューする組は、ドライブだけでなく幅広い場面で聴かれる前提で作る（2026-10-22）

- 場面：**ライブハウス**・**パーティ・クラブ**・**ひとりで聴く**（ヘッドホン・部屋・散歩・夜更かし）・**ドライブ**。新しい組は主な場面を 1 つと近い場面を 1〜2 つ持つ。最初の 5 組がドライブなので、それ以外を優先する
- 場面ごとの仕様（曲の長さ・サビの位置・ブレイクを使ってよいか・曲づくりの注意）は `_common.py` の `SCENE_TYPES`。表は `docs/03_artists.md`
- 管理表の「聴かれる場面」の先頭に主な場面を書く → 設定書の `persona.scene_type`・`sound.scene_spec` が自動で決まる
- 効く場所：Claude の新しい組の提案（`artist_book.py propose`・`expand_label.py`）／ブリーフ作り（場面に合わせた曲づくりと、ブレイクの可否）／毎週の話題曲の調べ（live・party・personal を追加）／Suno の曲の長さ（場面の長さのまん中）／取り込みのときの長さの確かめ（`select_takes.py`）
- 最初の 5 組（DECLAN FAY・HOLLOWPLAN・VERNALIGHT・SOFT CANTILEVER・TIDEWOOL）はドライブのまま変えない

## 30. 最初の 5 組も、定期配信では聴かれる場面を限定せずに伸ばす（2026-10-22。29 を広げる）

- 定期配信の曲ごとに、場面（ライブハウス・パーティ・クラブ・ひとりで聴く・ドライブ）を `templates/scene_plan.json` の割合でくじで選ぶ。週と組で決まる（やり直しても同じ）。前の週と同じ場面は 3 分の 1 に下げる
- 選んだ場面はブリーフの `scene` に入り、次のところで効く：
  | どこで | どう効くか |
  |---|---|
  | 参考曲の割り当て | その場面で伸びている話題曲を 1.5 倍選びやすい |
  | ブリーフ作り（Claude） | その曲の場面に合わせて編曲・勢い・形を変える。声・音色・癖・世界観は変えない。ドライブのためだけの禁止（急な無音・大きな音量差）は、ブレイクを使ってよい場面ではゆるめる |
  | Suno | 曲の長さ＝場面の長さのまん中。ブレイクを使ってよい場面では除外から silence を外す |
  | テイク選び | 長さ・サビの位置をその場面の決まりで確かめる |
- デビュー曲（今日からの 4 組）はドライブのまま。子レーベルの組はレーベルの場面のまま
- 割合（初期値）は docs/03_artists.md の表。配信が始まったら、場面ごとの再生の伸びを見て割合を直す

## 31. 組ごとに、場面別でよく伸びた曲をベースに厚みを出す（2026-10-22。30 を広げる）

- `collect_metrics.py` が曲ごとの場面（`out/metrics/release_scenes.csv`）を書き、`analyze_growth.py` が組ごと・場面ごとの伸び（1 日あたりの再生・保存率）を出す → `out/growth/scene_weights.json`
- 場面のくじ：`scene_plan.json` の割合 × 伸びの倍率（0.5〜3 倍）。よく伸びた場面の曲が増える
- ベースの曲：その場面でよく伸びた曲（組の平均の 1.2 倍以上）の作り方をブリーフに渡し、要素を引き継いで押し広げた兄弟の曲を作る。メロディ・歌詞は新しく。参考曲もベースの曲が借りたものを選びやすくする
- 詳しくは `docs/03_artists.md` の「よく伸びた場面を厚くし、よく伸びた曲をベースにする」

## 32. アーティスト写真を、配信サイトのアーティストのページに入れる（2026-10-22）

- DistroKid の登録画面には、アーティスト写真の欄が無い。写真は、配信が始まってアーティストのページができたあとに、各サイトのアーティスト向けの管理画面で入れる（DistroKid の案内も「各サービスでページを受け取って変える」）
- 対象：**Spotify for Artists**（正方形のプロフィール写真＋横長 2660×1140 のヘッダー。ページの受け取りは DistroKid の「Special Access」から）・**Apple Music for Artists**（正方形。2400×2400 以上がよい・最小 800×800・引き伸ばさない）・**Amazon Music for Artists**（正方形）
- `artist_photo.py`：今のアーティスト写真（半年ごとの刷新の最新 → 保管庫の写真）を、サイト用の形に整える（`out/visuals/<組>/profile/`）。入れた写真を記録し、写真を刷新したら「入れ直す」と出す
- ダッシュボードの「アーティスト写真」（`/photos`）→「〇〇に写真を入れる」：専用の Chrome でサイトが開く。Gon さんがサイトの写真の「編集」「アップロード」を押すと、ファイルを選ぶ画面の代わりに整えた画像が自動で選ばれる。**切り抜きの確認と「保存」は Gon さん**（公開されるため。システムはサイトのボタンを押さない）→ 案内の「保存した」で記録
- YouTube Music・TIDAL・Deezer などは、アーティストのページの受け取り方がそれぞれ違うので、今回は入れていない（必要になったら足す）

## 33. 曲ごとに「エピソード」を作り、歌詞をそこから書く（2026-10-22）

- 毎週のブリーフ作り（`write_brief.py`）で、Claude は歌詞の前に**この曲のエピソード**を決める（必須）：
  テーマ／いつ・どこで／**見たもの**／**聞いたもの**／**考えたこと**／**感じたこと**／**そして思ったこと**（サビの芯）／エピソードの文章（日本語 200〜400 字）／英語の短い紹介／生まれたもと（近況・歌の種・ベースの曲）
- 元にするもの：アーティストの人生（管理表）・今週の歌のもと（近況・歌の種）・その曲の聴かれる場面（ライブハウスの夜・パーティ・深夜の部屋 など）
- 歌詞はエピソードから書く：節（Verse）は見たもの・聞いたものを組の言葉に変えて、サビは「そして思ったこと」を運ぶ。控えめに具体的に、大げさにしない。実在の名前は入れない
- 見える場所：公開の準備のページ・スマホのページの「この曲のエピソード」／公開セットと保管庫の `<アーティスト名>_<曲名>_エピソード.md`／SNS の投稿文（英語の紹介を使う）
- デビュー曲 5 曲のエピソードは、歌の種（管理表）と歌詞から書き、作業セット（`debut_kit/2026-10-11/kit.json` の各曲の `episode`）に入れた

## 34. Suno のロボット確認が何度も出て通らない件への対応（2026-10-22）

- 原因の見当：入力のためにページに入れていた仕掛け（翻訳止め・部品の一覧・クリックで教える）が、ロボット確認の小さな画面（Cloudflare の iframe）の中にも入っていた。また、何曲か続けて入れるときは、Gon さんが Create を押す間もシステムが Chrome につながったままだった。ロボット確認は「自動操作の気配」があると何度でも出して通さない
- 直したこと：
  - 仕掛けは一番外の画面だけに入れる（iframe・challenges.cloudflare.com・hCaptcha・reCAPTCHA には入れない）
  - Suno は 1 回の「Suno に入力する」で 1 曲だけ。入れ終わったらすぐにシステムが Chrome から離れ、つながっていない状態で Gon さんが Create を押す。次の曲は少し時間をあけてもう一度押す
- それでも通らないとき：専用の Chrome は使わず、ふだんの Chrome か Safari で `http://localhost:8765/phone`（スマホのページ。Mac でも使える）を開き、「写す」ボタンで Suno に貼る。続けて何曲も作らない
